# EMSE 보강 분석: (A) holdout 사전등록, (B) 수동 검증

원고 ISRE-2026-4563의 두 약점을 막기 위한 계획과 도구입니다. 원고의 실제 데이터와 replication package는 이 저장소에 없습니다. 아래 스크립트는 입력 CSV 형식만 맞추면 바로 돌아가고, 합성 데이터로 동작을 확인했습니다.

---

## A. Holdout 재검증 사전등록 (OSF 등록용 초안)

### A.0 먼저 알아야 할 것: 오늘 이전의 출시는 holdout이 아닙니다

- 원고의 데이터 수집 종료 시점은 2026년 10월 5일 주이고, 38개 출시는 2023년 7월부터 2026년 7월까지입니다.
- 이 기간의 출시는 이미 추정치를 본 뒤에 통계량을 정한 데이터이므로 **확증용으로 쓸 수 없습니다.**
- 확증 분석은 **등록 시각 이후에 발표되는 출시만** 씁니다. 사전등록 타임스탬프가 신뢰성의 전부이므로, **분석 전에 OSF에 등록**하세요 (이 초안을 다듬어서 올리면 됩니다).
- 새 출시가 적게 나오면 검정력이 낮습니다. 원고는 38개 출시, 277개 repository-launch pair였습니다. 그래서 A.5의 최소 표본과 중단 규칙을 정했습니다.

### A.1 확증 가설 (H-conf)

> 업스트림 모델 출시에 노출된 저장소는, 노출되지 않은 저장소보다 출시 후 다음 릴리스까지의 시간이 짧다.

방향은 원고의 탐색 결과와 같은 단측 가설이지만, 검정은 원고와 동일하게 **양측 placebo p**로 보고합니다 (A.4).

### A.2 확증 통계량 (사전 고정)

| 항목 | 값 |
|---|---|
| 1차 통계량 | 출시 후 다음 릴리스까지 시간의 **restricted mean (28일에서 절단)**, 노출군 − 비노출군, 출시별 동일 가중 평균 |
| 대상 저장소 | 출시 전 90일 안에 릴리스가 한 번이라도 있었던 저장소 |
| 릴리스 | 원고의 정의 (draft·prerelease 제외, 모든 릴리스 포함: 핫픽스 포함) |
| 통제군 | 해당 출시 유형에 노출되지 않은 저장소 (원고의 "all launches" 사양) |
| 추론 | 원고 4.3절 그대로: 출시일을 출시 유형을 유지한 채 실제 출시에서 ±14일 이상 떨어진 placebo 날짜로 교체, 999회 반복, 양측 p |
| 확증 판정 | 1차 통계량이 placebo 분포에 대해 p < 0.05 이고 부호가 원고와 같음 (노출군이 더 빠름) |

**2차 통계량 (확증 판정에 쓰지 않고 보고만 함):** 1일 내 릴리스 비율 차이, 정규 릴리스만(핫픽스 제외), 다른 출시에 노출된 통제군을 제거한 사양. 원고에서 이 세 가지의 결과가 서로 달랐으므로(핫픽스 제외 시 p = 0.10), 같은 패턴이 다시 나오는지가 독립적인 정보입니다.

### A.3 출시와 노출 코딩 (분석 전에 동결)

1. **출시 목록:** 등록일 이후 (OpenAI, Anthropic, Google의 API 모델, 그리고 open-weights 모델) 공개 발표를 집계합니다. 포함 기준은 원고와 같이 "공개 발표일이 있는 새 모델 출시"이며, 기준 문서와 URL을 목록과 함께 남깁니다. 분석 중에 추가·삭제하지 않습니다.
2. **노출 코딩 (판단 의존성 제거):**
   - 코더 2명이 **서로 독립적으로** 저장소 × 출시 유형(open-weights, OpenAI, Anthropic, Google) 표를 채웁니다. 76칸입니다 (19 × 4).
   - 코드북 한 장: "이 저장소가 해당 유형의 모델을 직접 지원하는 코드나 인터페이스를 갖는가" (예: OpenAI SDK는 OpenAI API에 노출, vLLM은 open-weights에 노출). 근거 파일이나 문서 URL을 같이 기록합니다.
   - `kappa_exposure.py`로 κ를 계산하고, 불일치는 제3자 또는 합의로 해결합니다. **코더는 어떤 출시가 효과를 보였는지 모르는 상태**여야 합니다. 새 출시 결과를 보기 전에 코딩을 끝내고 동결하세요.
   - 기존 38개 출시용 코딩도 같은 방식으로 2인 독립 코딩해서 κ와 불일치 수를 보고합니다. 불일치 칸이 결과를 바꾸는지 민감도 분석을 합니다.
3. 저장소 목록은 원고의 19개로 고정합니다 (새 저장소 추가 없음).

### A.4 분석 코드

원고의 replication package 스크립트를 **수정 없이** 재사용하고, 입력만 새 출시로 교체합니다. 분석 코드의 해시를 등록에 포함하세요.

### A.5 표본 크기와 중단 규칙

- **최소 15개 출시**를 모을 때까지 기다립니다. 원고에서 출시 한 건당 노출 저장소가 약 7개(277 pair / 38 출시)였으므로 15개 출시는 약 100 pair입니다. 원고의 1/3 수준이어서 검정력은 낮습니다.
- 수집 창은 등록일부터 최대 6개월(예: 2027-04-30)까지이고, 그때까지 15개에 못 미치면 **있는 만큼 분석하고 "검정력 부족"으로 명시**합니다.
- **중간에 결과를 보지 않습니다.** 중단은 위 조건으로만 합니다.
- 효과 크기 해석: 원고의 추정치 3.4일은 선택 효과(winner's curse)로 부풀려졌을 수 있습니다. 확증 결과는 "효과가 재현되는가"와 "추정치가 얼마나 줄었는가"를 함께 보고합니다.

### A.6 결과 보고 계획

- 확증 통계량이 재현되면: "pre-registered holdout에서 재현"을 abstract와 본문에 올립니다.
- 재현되지 않으면: 원고의 일 단위 분석을 **exploratory로 강등**하고, 핫픽스와 오염된 통제군에 민감하다는 점을 한계로 씁니다. 그래도 EMSE는 이 정직한 보고를 받아줍니다.

## B. 수동 검증 프로토콜

대상 세 가지와 필요한 입력 형식입니다.

| 대상 | 표본 | 산출 | 입력 CSV 열 |
|---|---|---|---|
| (1) bug 분류 (라벨 또는 제목 키워드) | 100건 (분류 bug 50 + 비bug 50), 저장소 전체에서 무작위 | precision, recall, κ | `id,repo,title,labels,body,pred` |
| (2) 릴리스 노트의 모델 언급 매칭 | 100건 (매칭 50 + 비매칭 50) | precision, recall, κ | `id,repo,text,pred` |
| (3) 릴리스 노트의 fix 항목 분류 | 100건 (fix 50 + 비fix 50). 원고는 12건만 확인함 | precision, recall, κ | `id,repo,text,pred` |
| (4) 노출 코딩 | 76칸 전체 | κ | `repo,launch_type,exposed` |

**왜 반반 추출인가:** 무작위 100건에서 bug는 일부(원고에서 fix 항목이 평균 32%)라 recall을 잴 표본이 모자랍니다. 분류 결과로 층화해서 각 50건씩 뽑고, recall은 층 크기로 가중해 계산합니다 (`score.py`가 처리).

### B.1 절차

```bash
# 1) 표본 추출. key.csv는 코더에게 주지 않음. 코더별로 순서가 다른 빈 시트가 생김
python sample.py issues issues.csv out_issues --n 100 --seed 1
python sample.py notes  notes_model.csv out_model --n 100 --seed 2
python sample.py notes  notes_fix.csv   out_fix   --n 100 --seed 3

# 2) 두 코더가 sheet_coder1.csv, sheet_coder2.csv의 label 열(1/0)을 독립적으로 채움
#    (코더는 pred를 볼 수 없고, 서로의 시트도 볼 수 없음)

# 3) 불일치는 제3자가 adjudicated.csv (id,label)로 판정 후 채점
python score.py out_issues --adjudicated adjudicated.csv
python kappa_exposure.py coder1_exposure.csv coder2_exposure.csv
```

### B.2 코딩 기준 (코드북에 그대로 쓸 것)

- **bug:** "소프트웨어가 의도한 대로 동작하지 않는다는 보고" (크래시, 잘못된 출력, 회귀). 기능 요청, 질문, 문서 오류, 사용 문의는 bug가 아님.
- **모델 언급:** 릴리스 노트가 그 출시된 모델을 가리키는가 (일반 단어와 우연히 겹치는 경우 제외. 예: "claude"를 사람 이름 등으로 쓴 경우, 모델 계열을 가리키는 일반어).
- **fix 항목:** 항목이 기존 결함을 고친다. 기능 추가, 리팩터링, 의존성 갱신, 기여자 이름은 fix가 아님.

### B.3 보고할 것 (표 한 장)

| 분류기 | n | precision (95% CI) | recall (95% CI) | κ |
|---|---|---|---|---|
| bug | 100 | | | |
| 모델 언급 매칭 | 100 | | | |
| fix 항목 | 100 | | | |
| 노출 코딩 | 76 | n/a | n/a | |

### B.4 결과를 어떻게 쓸까

- precision과 recall이 높고 κ ≥ 0.7: 한계 문장을 "분류를 수동 검증했다(precision x, recall y)"로 교체.
- recall이 낮음: 기준을 사전에 정해둔 규칙으로 개선(예: 키워드 추가)하고, 개선 전후 결과가 같은지 민감도 분석. **결과를 보고 규칙을 고르지 않도록**, 어떤 규칙으로 바꿀지를 검증 표본과 다른 표본(개발용 100건)으로 정하세요.
- 오분류가 릴리스 나이에 따라 달라지는지(원고가 걱정한 편향)를 보려면, 표본에 `weeks_since_release` 열을 붙여 (a) 나이 구간별 precision, (b) 나이 구간별 recall을 따로 보고하세요. 원고 6.3절이 "배제하지 못한다"고 쓴 바로 그 부분입니다.

### B.5 필요한 인력과 시간

- 코더 2명 + 판정자 1명 (공저자 또는 대학원생). 각 시트 100건 × 3 = 300건과 노출 76칸으로 코더당 약 4–6시간으로 예상됩니다 (한 건에 1분 안팎).
- 코더가 연구 가설을 알면 편향이 생기므로, 가설을 설명하지 말고 코드북만 주세요.
